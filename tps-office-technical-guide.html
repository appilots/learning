1สถาปัตยกรรมระบบSystem Architectureシステムアーキテクチャ

หมวดนี้อธิบายว่าระบบเชื่อมต่อกับ SharePoint และ Azure อย่างไร สำหรับผู้ดูแลระบบ/ทีม IT เท่านั้น This section explains how the system connects to SharePoint and Azure — for system administrators / IT team only. このセクションでは、システムがSharePointおよびAzureとどのように接続しているかを説明します — システム管理者／IT担当者向けです。

ระบบใช้ Power Automate เป็น "สะพาน" อ่านข้อมูลจาก SharePoint แทนการต่อ Microsoft Graph API ตรงๆ เพราะ Connector ของ Power Automate ได้รับอนุมัติจาก Microsoft ไว้ล่วงหน้าแล้ว จึงไม่ติดปัญหา Admin Consent แบบที่เจอกับ Graph API The system uses Power Automate as a "bridge" to read data from SharePoint instead of connecting directly to Microsoft Graph API — Power Automate's connector is pre-approved by Microsoft, so it avoids the Admin Consent issue that direct Graph API access runs into. 本システムはPower Automateを「ブリッジ」として使用し、Microsoft Graph APIに直接接続する代わりにSharePointからデータを読み取ります。Power Automateのコネクタは事前にMicrosoftの承認を受けているため、Graph APIの直接接続で発生するAdmin Consentの問題を回避できます。

ลำดับการไหลของข้อมูล Data Flow Sequence データフローの順序

  1. พนักงาน ATTG เข้าเว็บผ่าน browser ที่ https://tpsit.attg.co.th An ATTG employee opens https://tpsit.attg.co.th in a browser. ATTGの従業員がブラウザでhttps://tpsit.attg.co.thにアクセスします。
  2. Azure App Service ตอบกลับหน้าเว็บ (React SPA ที่ Build ไว้ล่วงหน้า, จากโฟลเดอร์ api-appservice/public/) จาก Origin เดียวกันกับ API — ไม่มี Azure Static Web Apps คั่นกลางอีกต่อไป Front-end (React + Entra ID Sign-in) เรียก /api/* แบบ Relative Path เดิม แต่เป็น Origin เดียวกันเลย ไม่ใช่ Cross-Origin Azure App Service serves the web page (a pre-built React SPA, from the api-appservice/public/ folder) from the same origin as the API — Azure Static Web Apps no longer sits in between. The front-end (React + Entra ID sign-in) still calls /api/* as a relative path, but it's now the same origin, not cross-origin. Azure App Serviceは、Webページ（api-appservice/public/フォルダにある事前ビルド済みのReact SPA）をAPIと同じオリジンから配信します — Azure Static Web Appsはもはや間に存在しません。フロントエンド（React + Entra IDサインイン）は引き続き/api/*を相対パスで呼び出しますが、現在は同一オリジンであり、クロスオリジンではありません。
  3. Backend API (Express, บน Azure App Service) อ่าน Master Data จาก Azure SQL ที่ sync ไว้แล้ว และอ่าน/เขียนข้อมูล Project / Training / Power Champion โดยตรง — โค้ด Backend เดิมเขียนเป็น Azure Functions (api/) ปัจจุบัน Runtime จริงที่ Deploy ใช้งานคือ Express บน Azure App Service (api-appservice/) แทนทั้งหมด (ทั้ง Frontend และ Backend ในตัวเดียวกัน — ดูหมายเหตุด้านล่าง) โค้ด api/ ยังเก็บไว้ในโปรเจกต์เพื่ออ้างอิง แต่ไม่ใช่สิ่งที่รันอยู่จริงอีกต่อไป The Backend API (Express, on Azure App Service) reads Master Data from the already-synced Azure SQL database, and reads/writes Project / Training / Power Champion data directly — the original backend was written as Azure Functions (api/), but the actual deployed runtime today is entirely an Express app on Azure App Service (api-appservice/) instead (serving both frontend and backend from the one app — see the note below). The api/ code is kept in the project for reference but is no longer what's actually running. Backend API（Express、Azure App Service上）は、同期済みのAzure SQLからマスターデータを読み取り、Project／Training／Power Championのデータを直接読み書きします — 元のバックエンドはAzure Functions（api/）として作成されましたが、現在実際にデプロイされているランタイムは完全にAzure App Service上のExpressアプリ（api-appservice/）です（フロントエンドとバックエンドの両方を1つのアプリでホスト — 下記の注記を参照）。api/のコードは参照用にプロジェクト内に残されていますが、もはや実際に稼働しているものではありません。
  4. Power Automate Scheduled Flow (ทำงานทุก 30 นาที) ดึงข้อมูลจาก SharePoint List (Employee / Department / Division / Section) มาเขียนสำเนาล่าสุดลง Azure SQL — Backend ไม่เคยต่อ SharePoint โดยตรง A Power Automate Scheduled Flow (running every 30 minutes) pulls data from SharePoint Lists (Employee / Department / Division / Section) and writes the latest copy into Azure SQL — the backend never connects to SharePoint directly. Power Automateのスケジュールフロー（30分ごとに実行）がSharePointリスト（Employee／Department／Division／Section）からデータを取得し、最新のコピーをAzure SQLに書き込みます — バックエンドがSharePointに直接接続することはありません。
ทำไมต้องออกแบบแบบนี้: Why this design: なぜこの設計にしたのか：
  1. ใช้ทรัพยากร Azure ที่มีอยู่แล้วเป็นแกนหลัก ไม่ต้องสร้างใหม่ Uses existing Azure resources as the core, without needing to build anything new. 既存のAzureリソースを中核として活用し、新規構築を不要にします。
  2. ใช้ Power Automate เป็นสะพานที่ได้รับอนุมัติแล้ว (Approved Bridge) Uses Power Automate as an already-approved bridge. 承認済みのブリッジとしてPower Automateを使用します。
  3. หลีกเลี่ยงการต่อ Graph API ตรงๆ ซึ่งต้องขอ Admin Consent เพิ่ม — Power Automate connector ไม่ติดปัญหานี้ Avoids connecting to Graph API directly, which would require additional Admin Consent — the Power Automate connector doesn't run into this issue. 追加のAdmin Consentが必要となるGraph APIへの直接接続を回避します — Power Automateコネクタではこの問題は発生しません。

ย้ายทั้งระบบจาก Azure Static Web Apps + Functions → App Service เดียวFull Migration: Azure Static Web Apps + Functions → a Single App Service全面移行：Azure Static Web Apps + Functions → 単一のApp Service

เกิดเหตุขัดข้องระบบ 2 วัน จากการที่ AIAP (ทีมความปลอดภัยกลุ่ม) เปิดใช้ Private Network บน Azure SQL — ต้นเหตุแท้จริงคือขาด DNS Forwarding จากเครือข่ายภายในไปยัง Azure Private Link ไม่ใช่ปัญหาที่โค้ดแอป แต่เพื่อความง่ายในการดูแลและลดความซับซ้อนของเครือข่าย จึงย้าย ทั้ง Frontend และ Backend มารวมเป็น Express App เดียวบน Azure App Service (โฟลเดอร์ api-appservice/, ให้บริการทั้งไฟล์ React SPA ที่ Build ไว้แล้วผ่าน express.static() และ Route /api/* จากแอปเดียวกัน) แทนที่ Azure Static Web Apps + Azure Functions เดิม (api/) — Route/Logic ฝั่ง API เหมือนเดิมทุกจุด แต่สถาปัตยกรรมโฮสติ้งเปลี่ยนไปทั้งหมด ไม่ใช่แค่เปลี่ยน Runtime ของ Backend เพียงอย่างเดียว A 2-day outage occurred after AIAP (the group security team) enabled Private Network on Azure SQL — the real root cause was missing DNS forwarding from the on-prem network to the Azure Private Link, not an application code issue. For easier maintenance and to reduce network complexity, both the frontend and backend were consolidated into a single Express app on Azure App Service (the api-appservice/ folder, which serves the pre-built React SPA via express.static() and the /api/* routes from the very same app) — replacing the original Azure Static Web Apps + Azure Functions setup (api/) entirely. The API-side routes/logic are identical, but the hosting architecture changed completely, not just the backend runtime. AIAP（グループセキュリティチーム）がAzure SQLでPrivate Networkを有効化した後、2日間のシステム障害が発生しました — 真の原因は、オンプレミスネットワークからAzure Private Linkへの DNSフォワーディングが欠落していたことであり、アプリケーションコードの問題ではありませんでした。保守の容易さとネットワークの複雑さを軽減するため、フロントエンドとバックエンドの両方が、Azure App Service上の単一のExpressアプリ（api-appservice/フォルダ。事前ビルド済みのReact SPAをexpress.static()で配信し、/api/*ルートも同じアプリから提供）に統合され、元のAzure Static Web Apps + Azure Functions構成（api/）を完全に置き換えました。APIサイドのルート／ロジックは同一ですが、ホスティングアーキテクチャ全体が変更されており、バックエンドのランタイムだけの変更ではありません。

แก้ไขข้อมูลถูก apply แบบ optimistic ใน local state ก่อนแล้วขึ้น toast สำเร็จทันที — ถ้า sync ไป API จริงล้มเหลว (เช่น token หมดอายุ) จะไม่มีอะไรแจ้งเตือนเลย ผู้ใช้เห็น "สำเร็จ" แต่ข้อมูลไม่ถึง server จริง แก้โดยให้ setValue คืนค่า Promise ที่ผู้เรียก await เพื่อขึ้น toast เตือนซ้ำถ้า sync ล้มเหลวจริง Edits were applied optimistically to local state first, showing a success toast immediately — if the background sync to the real API actually failed (e.g. an expired token), nothing surfaced that. The user saw "success" but the change never reached the server. Fixed by having setValue return a Promise the caller awaits, to show a follow-up warning toast if the sync genuinely failed. 編集内容はまずローカル状態に楽観的に反映され、即座に成功トーストが表示されていました — バックグラウンドでの実際のAPI同期が失敗した場合（例：トークン期限切れ）でも何も表示されませんでした。ユーザーには「成功」と見えても、変更は実際にはサーバーに届いていませんでした。setValueがPromiseを返すようにし、呼び出し元がawaitすることで、同期が本当に失敗した場合には警告トーストを追加表示するよう修正しました。

Denominator ไม่ตรงกันระหว่างยอดรวมกับยอดแยกส่วนDenominator mismatch between group-wide and scoped totals全体集計と部分集計の分母の不一致

Section Dashboard เคยแสดง 8.2% ข้างๆ ยอดรวมทั้งบริษัท 0.2% เพราะหารด้วยฐานคนละแบบ (headcount ดิบ vs. จำนวน License O365) แก้ด้วย estimateLicensedHeadcount() ที่ประเมินสัดส่วน License ตามสัดส่วน headcount ของแต่ละขอบเขต ให้ทุกมุมมองหารด้วยฐานเดียวกันเสมอ Section Dashboard once showed 8.2% next to a group-wide 0.2%, purely because the two divided by different kinds of denominator (raw headcount vs. O365 license count). Fixed with estimateLicensedHeadcount(), which estimates each scope's proportional slice of the license total, so every view divides by the same kind of denominator. Section Dashboardでは、分母の種類が異なっていた（生の従業員数 vs. O365ライセンス数）ため、全社の0.2%の隣に8.2%と表示されていたことがありました。estimateLicensedHeadcount()で各スコープのライセンス総数に対する比例配分を推定するよう修正し、すべての表示で同じ種類の分母を使用するようにしました。

คอลัมน์ INT ปัดทิ้งเศษนาทีเงียบๆ ทุกครั้งที่บันทึกAn INT column silently rounded away the minutes portion on every saveINTカラムが保存のたびに分を静かに切り捨てていた

หลังเปลี่ยนฟอร์มให้กรอกชั่วโมง+นาทีแยก 2 ช่อง (16 ชม. 20 นาที → 16.333) คอลัมน์ Projects.savingHours/PowerChampions.savingHoursPerYear ยังเป็น INT เดิม ทำให้ทศนิยมถูกปัดทิ้งทุกครั้งที่บันทึก — ผู้ใช้แก้ไขนาที กดบันทึก แล้วเปิดกลับมาดูเจอนาทีหายไปเสมอ (รายงานโดยผู้ใช้: "ช่องนาที บันทึกแล้ว ไม่ Save เมื่อแก้ไข") ตรวจสอบพบด้วยการรันคำสั่ง Save/Read ผ่านโค้ด Repository ตรงๆ แล้วเห็นค่ากลับมาเป็นจำนวนเต็มเสมอ แก้ด้วยการขยายคอลัมน์เป็น DECIMAL(10,4) ทั้ง 2 ตาราง (ทั้ง Migration ใน schema.sql และแก้ Type ในโค้ด Repository) แล้ว Restart Backend Server เพื่อให้โค้ดที่แก้มีผลจริง (แก้แค่ไฟล์เฉยๆ ไม่พอ ต้อง Restart Process ด้วย) After the form was changed to collect hours+minutes as 2 separate fields (16 hrs 20 min → 16.333), the Projects.savingHours/PowerChampions.savingHoursPerYear columns were still the original INT, so the decimal got rounded away on every save — a user would edit the minutes, save, reopen the record, and always find the minutes gone (reported by the user: "the minutes field, after saving, isn't saved when edited"). Confirmed by running a direct Save/Read through the repository code and observing the value always came back as a whole integer. Fixed by widening both columns to DECIMAL(10,4) (both the schema.sql migration and the type in the repository code), then restarting the backend server so the code change actually took effect — editing the file alone wasn't enough, the running process had to be restarted too. フォームが時間＋分の2つの別項目を収集するように変更された後（16時間20分→16.333）、Projects.savingHours／PowerChampions.savingHoursPerYearカラムは元のINTのままだったため、保存のたびに小数が切り捨てられていました — ユーザーが分を編集して保存し、レコードを開き直すと常に分が消えていました（ユーザー報告：「分の項目が、保存しても編集時に保存されない」）。リポジトリコードを通じて直接Save／Readを実行し、値が常に整数として返ってくることを確認して原因を特定しました。両カラムをDECIMAL(10,4)に拡張して修正しました（schema.sqlのマイグレーションとリポジトリコードの型の両方）。その後、コードの変更を実際に反映させるためバックエンドサーバーを再起動しました — ファイルを編集するだけでは不十分で、実行中のプロセスも再起動する必要がありました。

ตัวกรอง "แผนก" ไม่มีตัวเลือกสำหรับหน่วยงานที่ไม่มีใน Master DataDepartment filter had no option for units missing from Master DataMaster Dataに存在しない部署は「部署」フィルターに選択肢がなかった

ตัวเลือกในช่อง แผนก/ส่วน/ฝ่าย ของฟอร์ม Project Registration ดึงมาจากรายชื่อพนักงานที่ Sync จาก SharePoint เท่านั้น (MasterEmployees) และไม่มี allowCustom เหมือนช่องผู้อนุมัติ — พบกรณีจริงที่ AT-A ไม่มีพนักงานคนไหนสังกัดแผนก "IT System Management"/"IT Project Management" ใน Master Data เลย ทำให้ผู้ใช้กรอกแผนกนี้ไม่ได้เลยตั้งแต่ต้น (Project ที่พยายามกรอกแผนกนี้เลยมีค่าแผนกว่างเปล่า) แก้โดยเปิด allowCustom ให้ 3 ช่องนี้ และรวมตัวเลือก Dropdown จากทั้ง Master Data และ ค่าที่เคยถูกพิมพ์ไว้ในการลงทะเบียน Project ของบริษัทนั้นๆ เพื่อให้ค่าที่พิมพ์เองครั้งแรกกลายเป็นตัวเลือกให้คนถัดไปทันที The Department/Section/Division dropdown options in the Project Registration form came only from the SharePoint-synced employee list (MasterEmployees), and unlike the approver fields, had no allowCustom. A real case surfaced where AT-A had zero employees under "IT System Management"/"IT Project Management" in Master Data at all, so a user had no way to enter that department in the first place (the affected Project ended up with an empty department field). Fixed by enabling allowCustom on all 3 fields, and merging the dropdown options from both Master Data and whatever values are already used on that company's own registered Projects, so the first free-typed entry immediately becomes an option for the next person. Project RegistrationフォームのDepartment／Section／Divisionドロップダウンの選択肢は、SharePoint同期済みの従業員リスト（MasterEmployees）のみから取得されており、承認者フィールドとは異なりallowCustomが設定されていませんでした。AT-Aには「IT System Management」／「IT Project Management」に所属する従業員がMaster Dataに1人も存在しないという実例が発生し、ユーザーはそもそもこの部署を入力する方法がありませんでした（該当のProjectは部署欄が空のまま登録されていました）。3つのフィールドすべてにallowCustomを有効化し、Master Dataとその会社の登録済みProjectで既に使用されている値の両方からドロップダウンの選択肢をマージすることで修正しました。これにより、最初に自由入力された値が次のユーザーにとって即座に選択肢となります。
