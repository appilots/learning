1สถาปัตยกรรมระบบ

หมวดนี้อธิบายว่าระบบเชื่อมต่อกับ SharePoint และ Azure อย่างไร สำหรับผู้ดูแลระบบ/ทีม IT เท่านั้น

ระบบใช้ Power Automate เป็น "สะพาน" อ่านข้อมูลจาก SharePoint แทนการต่อ Microsoft Graph API ตรงๆ เพราะ Connector ของ Power Automate ได้รับอนุมัติจาก Microsoft ไว้ล่วงหน้าแล้ว จึงไม่ติดปัญหา Admin Consent แบบที่เจอกับ Graph API

ลำดับการไหลของข้อมูล

  1. พนักงาน ATTG เข้าเว็บผ่าน browser ที่ https://tpsit.attg.co.th
  2. Azure Static Web App (React front-end + Entra ID Sign-in) เรียก /api/*
  3. Azure Functions (Backend API) อ่าน Master Data จาก Azure SQL ที่ sync ไว้แล้ว และอ่าน/เขียนข้อมูล Project / Training / Power Champion โดยตรง
  4. Power Automate Scheduled Flow (ทำงานทุก 30 นาที) ดึงข้อมูลจาก SharePoint List (Employee / Department / Division / Section) มาเขียนสำเนาล่าสุดลง Azure SQL — Functions ไม่เคยต่อ SharePoint โดยตรง
ทำไมต้องออกแบบแบบนี้:
  1. ใช้ทรัพยากร Azure ที่มีอยู่แล้วเป็นแกนหลัก ไม่ต้องสร้างใหม่
  2. ใช้ Power Automate เป็นสะพานที่ได้รับอนุมัติแล้ว (Approved Bridge)
  3. หลีกเลี่ยงการต่อ Graph API ตรงๆ ซึ่งต้องขอ Admin Consent เพิ่ม — Power Automate connector ไม่ติดปัญหานี้

2Tech Stack ที่ใช้สร้างระบบ

เทคโนโลยีหลักที่ใช้สร้างและรันระบบ TPS Office Digital Tools แบ่งตามชั้นการทำงาน

Cloud Service Model
PaaS (Platform as a Service) ทั้งหมด — ไม่มีส่วนไหนเป็น IaaS (ไม่ต้องดูแล VM/OS เอง) หรือ SaaS (เขียนโค้ดเองทั้งหมด ไม่ใช่ซอฟต์แวร์สำเร็จรูป)
Frontend
React (SPA) + Vite, Tailwind CSS, Recharts (กราฟ), lucide-react (ไอคอน)
Backend API
Azure Functions (Node.js, v4 programming model) รันแบบ co-located กับ Static Web App
Database
Azure SQL Database (Serverless tier)
Hosting
Azure Static Web Apps (Free tier)
Authentication
Microsoft Entra ID (Azure AD) — ใช้บัญชี O365 ของ ATTG ล็อกอิน
Master Data Source
SharePoint Online (ผ่าน Power Automate Scheduled Flow ดูหมวด 1)
Version Control
Git — เก็บใน private repository
Export
Excel export/import (ฝั่งไคลเอนต์) สำหรับ Project Registration และ Training

เหตุผลที่จัดเป็น PaaS ทั้งหมด

Azure Static Web AppsPaaS — host เว็บให้เลย ไม่ต้องดูแล server/OS เอง
Azure FunctionsPaaS (เจาะจงเรียก Serverless/FaaS) — รันโค้ด backend โดยไม่ต้องมี server ให้ดูแล จ่ายตามการใช้งานจริง
Azure SQL DatabasePaaS — ฐานข้อมูลจัดการให้ครบ (patch, backup, scaling) ไม่ต้องตั้ง VM ฐานข้อมูลเอง
Entra ID (Azure AD)PaaS/IDaaS — บริการ identity/login สำเร็จรูป
การเลือกใช้ PaaS ล้วนๆ นี่แหละที่ทำให้ต้นทุนต่ำ (Free tier + Serverless auto-pause, ดูหมวด 3 และ 4) และไม่ต้องมีคนคอย patch/ดูแล server เลย

3ฐานข้อมูล (Database)

รายละเอียดฐานข้อมูลจริงที่ใช้งานอยู่ — ดูรายชื่อ Table และ field แต่ละตัวแบบสดได้ที่หน้า Administration ในแอป (เมนู Database)

Auto-pauseหลังไม่มีการใช้งาน 60 นาที (ปลุกกลับมาเองอัตโนมัติเมื่อมี request เข้ามา)
วิธีเชื่อมต่อConnection string เก็บใน App Settings ของ Azure Functions — ยังไม่ใช้ Managed Identity เพราะต้องใช้ Static Web Apps ระดับ Standard (มีค่าใช้จ่ายเพิ่ม), ปัจจุบันใช้ Free tier

ดูรายชื่อ Table และ Field แบบสด (Live)

หน้า Administration → Database ในแอปจริง จะดึงรายชื่อ Table, จำนวนแถว และ Field ของแต่ละ Table ผ่าน sys.tables / sys.columns โดยตรงจากฐานข้อมูล ทุกครั้งที่เปิดหน้า — ข้อมูลจึงถูกต้องเสมอโดยไม่ต้องมาแก้เอกสารนี้ตามหลัง

หมายเหตุด้านต้นทุน: ค่าใช้จ่ายจริงอิงราคา Retail ของ Azure สำหรับ SKU นี้ (Southeast Asia) อยู่ที่ $0.620892/vCore-hour — ดูตัวเลขประมาณการรายเดือน 3 สถานการณ์ (ไม่มี keep-alive / keep-alive เฉพาะเวลาทำงาน / เปิดตลอด 24/7) ได้ที่หน้า Administration ในแอปเช่นกัน

4ข้อจำกัดของแพลตฟอร์ม

ข้อจำกัดจริงของ tier ที่ใช้อยู่ (Free / Serverless) ที่ทีม dev ควรรู้ก่อนออกแบบ feature ใหม่ที่ทำงานหนักหรือใช้เวลานาน

Function TimeoutAzure Static Web Apps (Free tier) มี hard timeout ที่ระดับแพลตฟอร์ม 45 วินาที ต่อ 1 request ไปยัง Azure Functions — ตั้งค่า timeout ในโค้ดให้นานกว่านี้ไม่มีผล เพราะแพลตฟอร์มตัดก่อน
Database Auto-pauseAzure SQL Serverless จะพักการทำงานหลังไม่มีการใช้งาน 60 นาที การ request แรกหลังพักจะช้ากว่าปกติ (cold start) เพราะต้องรอฐานข้อมูลตื่นก่อน
SLAStatic Web Apps ระดับ Free ไม่มี SLA (Service Level Agreement) รับประกัน uptime — หากต้องการ SLA ต้องอัปเกรดเป็นระดับ Standard
Custom Domainต้องพึ่ง DNS ภายนอก (เช่น DNS ของโรงงาน) ในการ resolve โดเมนที่กำหนดเอง — หาก DNS นั้นมีปัญหา ผู้ใช้ยังเข้าได้ผ่าน hostname ตรงของ Azure Static Web Apps เสมอ (ดูหมวด "การเข้าใช้งานสำรอง" ด้านล่าง)
Administration → Database ในแอปใช้เวลาตอบสนองของ query "list tables" (เกิน ~2.5 วินาที) เป็นตัวบ่งชี้ว่าฐานข้อมูลเพิ่ง resume จากการ pause หรือไม่ — ไม่ใช่การเช็คสถานะผ่าน Azure Resource Manager โดยตรง

5การสำรองข้อมูล

ระบบสำรองข้อมูลอัตโนมัติของแต่ละส่วน โดยไม่ต้องมี job หรือ script แยกต่างหาก

ฐานข้อมูล (Azure SQL)

Azure SQL Database สำรองข้อมูลให้อัตโนมัติทุกฐานข้อมูล (full + differential + transaction log backup) และรองรับ Point-in-Time Restore ย้อนหลังได้ตามระยะเวลาที่ Azure กำหนดไว้เป็นค่าเริ่มต้น — ไม่ต้องตั้ง backup job เพิ่มเอง

Source Code

เก็บด้วย Git และมี remote backup อยู่ใน private repository บน GitHub แยกจากเครื่อง local — ป้องกันข้อมูล source code สูญหายหากเครื่องที่พัฒนามีปัญหา

Master Data (SharePoint)

ข้อมูลต้นทาง (Employee / Department / Division / Section) อยู่ที่ SharePoint Online ซึ่งอยู่ภายใต้นโยบายสำรองข้อมูลมาตรฐานของ Microsoft 365 อยู่แล้ว
