1สถาปัตยกรรมระบบSystem Architectureシステムアーキテクチャ

หมวดนี้อธิบายว่าระบบเชื่อมต่อกับ SharePoint และ Azure อย่างไร สำหรับผู้ดูแลระบบ/ทีม IT เท่านั้น This section explains how the system connects to SharePoint and Azure — for system administrators / IT team only. このセクションでは、システムがSharePointおよびAzureとどのように接続しているかを説明します — システム管理者／IT担当者向けです。

ระบบใช้ Power Automate เป็น "สะพาน" อ่านข้อมูลจาก SharePoint แทนการต่อ Microsoft Graph API ตรงๆ เพราะ Connector ของ Power Automate ได้รับอนุมัติจาก Microsoft ไว้ล่วงหน้าแล้ว จึงไม่ติดปัญหา Admin Consent แบบที่เจอกับ Graph API The system uses Power Automate as a "bridge" to read data from SharePoint instead of connecting directly to Microsoft Graph API — Power Automate's connector is pre-approved by Microsoft, so it avoids the Admin Consent issue that direct Graph API access runs into. 本システムはPower Automateを「ブリッジ」として使用し、Microsoft Graph APIに直接接続する代わりにSharePointからデータを読み取ります。Power Automateのコネクタは事前にMicrosoftの承認を受けているため、Graph APIの直接接続で発生するAdmin Consentの問題を回避できます。

ลำดับการไหลของข้อมูล Data Flow Sequence データフローの順序

  1. พนักงาน ATTG เข้าเว็บผ่าน browser ที่ https://tpsit.attg.co.th An ATTG employee opens https://tpsit.attg.co.th in a browser. ATTGの従業員がブラウザでhttps://tpsit.attg.co.thにアクセスします。
  2. Azure Static Web App (React front-end + Entra ID Sign-in) เรียก /api/* The Azure Static Web App (React front-end + Entra ID sign-in) calls /api/*. Azure Static Web App（Reactフロントエンド + Entra IDサインイン）が/api/*を呼び出します。
  3. Azure Functions (Backend API) อ่าน Master Data จาก Azure SQL ที่ sync ไว้แล้ว และอ่าน/เขียนข้อมูล Project / Training / Power Champion โดยตรง Azure Functions (backend API) reads Master Data from the already-synced Azure SQL database, and reads/writes Project / Training / Power Champion data directly. Azure Functions（バックエンドAPI）は、同期済みのAzure SQLからマスターデータを読み取り、Project／Training／Power Championのデータを直接読み書きします。
  4. Power Automate Scheduled Flow (ทำงานทุก 30 นาที) ดึงข้อมูลจาก SharePoint List (Employee / Department / Division / Section) มาเขียนสำเนาล่าสุดลง Azure SQL — Functions ไม่เคยต่อ SharePoint โดยตรง A Power Automate Scheduled Flow (running every 30 minutes) pulls data from SharePoint Lists (Employee / Department / Division / Section) and writes the latest copy into Azure SQL — Functions never connects to SharePoint directly. Power Automateのスケジュールフロー（30分ごとに実行）がSharePointリスト（Employee／Department／Division／Section）からデータを取得し、最新のコピーをAzure SQLに書き込みます — FunctionsがSharePointに直接接続することはありません。
ทำไมต้องออกแบบแบบนี้: Why this design: なぜこの設計にしたのか：
  1. ใช้ทรัพยากร Azure ที่มีอยู่แล้วเป็นแกนหลัก ไม่ต้องสร้างใหม่ Uses existing Azure resources as the core, without needing to build anything new. 既存のAzureリソースを中核として活用し、新規構築を不要にします。
  2. ใช้ Power Automate เป็นสะพานที่ได้รับอนุมัติแล้ว (Approved Bridge) Uses Power Automate as an already-approved bridge. 承認済みのブリッジとしてPower Automateを使用します。
  3. หลีกเลี่ยงการต่อ Graph API ตรงๆ ซึ่งต้องขอ Admin Consent เพิ่ม — Power Automate connector ไม่ติดปัญหานี้ Avoids connecting to Graph API directly, which would require additional Admin Consent — the Power Automate connector doesn't run into this issue. 追加のAdmin Consentが必要となるGraph APIへの直接接続を回避します — Power Automateコネクタではこの問題は発生しません。

เหตุผลที่จัดเป็น PaaS ทั้งหมดWhy everything is classified as PaaSすべてPaaSに分類する理由

Azure Static Web Apps PaaS — host เว็บให้เลย ไม่ต้องดูแล server/OS เอง PaaS — hosts the website for you, no need to manage the server/OS yourself. PaaS — Webサイトをそのままホスティングし、サーバー／OSの管理は不要です。
Azure Functions PaaS (เจาะจงเรียก Serverless/FaaS) — รันโค้ด backend โดยไม่ต้องมี server ให้ดูแล จ่ายตามการใช้งานจริง PaaS (more specifically Serverless/FaaS) — runs backend code without a server to manage, billed based on actual usage. PaaS（より正確にはServerless／FaaS）— 管理すべきサーバーなしでバックエンドコードを実行し、実際の使用量に応じて課金されます。
Azure SQL Database PaaS — ฐานข้อมูลจัดการให้ครบ (patch, backup, scaling) ไม่ต้องตั้ง VM ฐานข้อมูลเอง PaaS — the database is fully managed (patching, backup, scaling); no need to set up a database VM yourself. PaaS — パッチ適用、バックアップ、スケーリングを含め完全に管理されており、自分でデータベースVMを構築する必要はありません。
Entra ID (Azure AD) PaaS/IDaaS — บริการ identity/login สำเร็จรูป PaaS/IDaaS — a ready-made identity/login service. PaaS／IDaaS — 既製のID／ログインサービスです。
การเลือกใช้ PaaS ล้วนๆ นี่แหละที่ทำให้ต้นทุนต่ำ (Free tier + Serverless auto-pause, ดูหมวด 3 และ 4) และไม่ต้องมีคนคอย patch/ดูแล server เลย Choosing an all-PaaS approach is exactly what keeps costs low (Free tier + Serverless auto-pause — see sections 3 and 4) and eliminates the need for anyone to patch/maintain servers at all. PaaSのみを採用することで、コストを低く抑えられ（Free tier＋Serverlessの自動一時停止 — セクション3・4参照）、サーバーのパッチ適用・保守を行う担当者も不要になります。

4ข้อจำกัดของแพลตฟอร์มPlatform Limitationsプラットフォームの制限

ข้อจำกัดจริงของ tier ที่ใช้อยู่ (Free / Serverless) ที่ทีม dev ควรรู้ก่อนออกแบบ feature ใหม่ที่ทำงานหนักหรือใช้เวลานาน The real limitations of the tiers in use (Free / Serverless) that the dev team should know before designing new features that are heavy or long-running. 重い処理や長時間実行される新機能を設計する前に、開発チームが知っておくべき、現在使用中のプラン（Free／Serverless）の実際の制限事項。

Function Timeout Azure Static Web Apps (Free tier) มี hard timeout ที่ระดับแพลตฟอร์ม 45 วินาที ต่อ 1 request ไปยัง Azure Functions — ตั้งค่า timeout ในโค้ดให้นานกว่านี้ไม่มีผล เพราะแพลตฟอร์มตัดก่อน Azure Static Web Apps (Free tier) has a platform-level hard timeout of 45 seconds per request to Azure Functions — setting a longer timeout in code has no effect, because the platform cuts it off first. Azure Static Web Apps（Free tier）には、Azure Functionsへの1リクエストあたり45秒のプラットフォームレベルのハードタイムアウトがあります — コード側でこれより長いタイムアウトを設定しても、プラットフォームが先に切断するため効果はありません。
Database Auto-pause Azure SQL Serverless จะพักการทำงานหลังไม่มีการใช้งาน 60 นาที การ request แรกหลังพักจะช้ากว่าปกติ (cold start) เพราะต้องรอฐานข้อมูลตื่นก่อน Azure SQL Serverless pauses after 60 minutes of inactivity. The first request after a pause will be slower than usual (cold start) because it has to wait for the database to wake up first. Azure SQL Serverlessは60分間操作がないと一時停止します。一時停止後の最初のリクエストは、データベースの起動を待つ必要があるため（コールドスタート）、通常より遅くなります。
SLA Static Web Apps ระดับ Free ไม่มี SLA (Service Level Agreement) รับประกัน uptime — หากต้องการ SLA ต้องอัปเกรดเป็นระดับ Standard The Free tier of Static Web Apps has no SLA (Service Level Agreement) guaranteeing uptime — an SLA requires upgrading to the Standard tier. Static Web AppsのFree tierには、稼働率を保証するSLA（Service Level Agreement）がありません — SLAが必要な場合はStandardプランへのアップグレードが必要です。
Custom Domain ต้องพึ่ง DNS ภายนอก (เช่น DNS ของโรงงาน) ในการ resolve โดเมนที่กำหนดเอง — หาก DNS นั้นมีปัญหา ผู้ใช้ยังเข้าได้ผ่าน hostname ตรงของ Azure Static Web Apps เสมอ (ดูหมวด "การเข้าใช้งานสำรอง" ด้านล่าง) Relies on external DNS (e.g. the factory's DNS) to resolve the custom domain — if that DNS has issues, users can always still access the app via the direct Azure Static Web Apps hostname (see the "Backup Access" section below). カスタムドメインの解決には外部DNS（例：工場のDNS）に依存します — そのDNSに問題が発生した場合でも、ユーザーは常にAzure Static Web Appsの直接のホスト名からアクセスできます（下記の「代替アクセス方法」セクションを参照）。
Administration → Database ในแอปใช้เวลาตอบสนองของ query "list tables" (เกิน ~2.5 วินาที) เป็นตัวบ่งชี้ว่าฐานข้อมูลเพิ่ง resume จากการ pause หรือไม่ — ไม่ใช่การเช็คสถานะผ่าน Azure Resource Manager โดยตรง The Administration → Database page in the app uses the response time of the "list tables" query (over ~2.5 seconds) as an indicator of whether the database just resumed from a pause — it is not a direct status check via Azure Resource Manager. アプリのAdministration → Databaseページでは、「list tables」クエリの応答時間（約2.5秒超）を、データベースが一時停止から復帰したばかりかどうかの指標として使用しています — Azure Resource Managerを介した直接的なステータスチェックではありません。

5การสำรองข้อมูลBackupsバックアップ

ระบบสำรองข้อมูลอัตโนมัติของแต่ละส่วน โดยไม่ต้องมี job หรือ script แยกต่างหาก The automatic backup mechanisms for each component, with no separate job or script required. 各コンポーネントの自動バックアップの仕組み — 別途ジョブやスクリプトを用意する必要はありません。

ฐานข้อมูล (Azure SQL)Database (Azure SQL)データベース（Azure SQL）

Azure SQL Database สำรองข้อมูลให้อัตโนมัติทุกฐานข้อมูล (full + differential + transaction log backup) และรองรับ Point-in-Time Restore ย้อนหลังได้ตามระยะเวลาที่ Azure กำหนดไว้เป็นค่าเริ่มต้น — ไม่ต้องตั้ง backup job เพิ่มเอง Azure SQL Database automatically backs up every database (full + differential + transaction log backups) and supports Point-in-Time Restore going back for the retention period Azure sets by default — no need to set up an additional backup job. Azure SQL Databaseは、すべてのデータベースを自動的にバックアップします（フルバックアップ＋差分バックアップ＋トランザクションログバックアップ）。Azureのデフォルト保持期間内であればPoint-in-Time Restore（特定時点への復元）にも対応しており、別途バックアップジョブを設定する必要はありません。

Source Code

เก็บด้วย Git และมี remote backup อยู่ใน private repository บน GitHub แยกจากเครื่อง local — ป้องกันข้อมูล source code สูญหายหากเครื่องที่พัฒนามีปัญหา Stored with Git, with a remote backup in a private repository on GitHub, separate from the local machine — protects the source code from being lost if the development machine has an issue. Gitで管理し、開発用マシンとは別に、GitHub上のプライベートリポジトリにリモートバックアップを保持しています — 開発マシンに問題が発生してもソースコードの消失を防ぎます。

Master Data (SharePoint)

ข้อมูลต้นทาง (Employee / Department / Division / Section) อยู่ที่ SharePoint Online ซึ่งอยู่ภายใต้นโยบายสำรองข้อมูลมาตรฐานของ Microsoft 365 อยู่แล้ว The source data (Employee / Department / Division / Section) lives in SharePoint Online, which is already covered by Microsoft 365's standard backup policies. 元データ（Employee／Department／Division／Section）はSharePoint Onlineにあり、Microsoft 365の標準バックアップポリシーの対象に既に含まれています。
